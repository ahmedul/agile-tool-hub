# Pilot invitations and session feedback

Invite facilitators to try a real workflow and report the first point of friction. The goal is ten teams choosing to run two sessions. The tracker starts with five existing-contact slots and five coach/trainer slots; these are planning slots, not researched or contacted recipients. Confirm the audience and actual recipients before sending.

Keep contact details in the owner's private address book. Use the team aliases in [the tracker](pilot-tracker.csv) for campaign notes. Record an opt-in, a completed session, and a second session separately.

## Follow up with someone who opted in

Hi [Name], thanks for trying the session. Three things would help me decide what to improve:

1. Could everyone join and complete the first useful action?
2. What was the first confusing or frustrating step?
3. Would you choose it for your next suitable session, and what would change that decision?

There’s no need to share private backlog contents. A description of the workflow problem is enough. If you would like me to quote feedback publicly, I’ll confirm the wording with you first.

## Record the first and second session

For each team, record whether the session actually happened and what decision or output it produced. At the second session, ask whether the earlier friction was still present and whether the facilitator selected the tool without prompting. A room creation event alone does not establish team adoption.

## Community answer examples

Adapt these to an existing relevant question. Keep the explanation in the reply, and include a tool link only where the community permits it.

### A ticket that another person can reproduce

For a checkout failure, I would separate what was observed from what is still a hypothesis. “Two requests appeared after pressing Pay twice” is an observation; “the shopper was charged twice” needs payment evidence. Add the initial state, exact repeated action, expected outcome, observed result, environment, and the open question about retries. Someone should be able to attempt reproduction from the ticket alone.

### Different Planning Poker votes

A spread of 2, 3, and 8 can mean people are estimating different scopes. Ask the highest and lowest voters which assumptions caused the difference. If one person expects an API change and another assumes the API already supports the query, resolve that before voting again. The discussion is the useful result; averaging the first votes can hide the disagreement.

Optional disclosure: I build a free Planning Poker tool and use this scenario in its workshop kit. Share the kit only if it directly answers the question and the community allows the link.

### A holiday in sprint capacity

Use consistent units. A one-day holiday affecting five people scheduled for eight hours removes 40 team-hours. If the working-day count already excluded that holiday, subtract nothing further. Then account for leave, meetings, and support across the same team. Upcoming availability and past completed points are different planning inputs; there is no general points-per-developer quota.

Optional disclosure: I build AgileToolHub. The capacity guide has a five-person worked example that keeps those deductions separate.
