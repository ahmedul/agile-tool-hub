Estimate story points by comparing a well-understood piece of work with stories your team has already completed. Discuss implementation effort, technical complexity, and uncertainty, then agree on a relative size. The estimate helps a team plan; it does not promise a delivery date.

Use the [Story Point Calculator](/tools/story-point-calculator) for a structured starting discussion, or open [Planning Poker](/tools/planning-poker) for simultaneous team voting. The examples below are illustrative sizes for one fictional team, not a conversion chart for other teams.

## 1. Agree on what the story includes

Start with the user outcome, [acceptance criteria](/templates/acceptance-criteria-template), dependencies, and the [Definition of Done](/tools/definition-of-done-checklist). Include testing, review, accessibility, and release work that the team needs to consider the story complete.

For example, “add a password-reset link” could mean adding a link to an existing flow or building token issuance, email delivery, expiry, and abuse protection. Those are different scopes. Clarify the boundary before choosing a number.

## 2. Pick a reference story

Choose a recently completed story the team remembers. Record its original scope and why it represents a useful reference. Build a small set covering smaller and larger work; avoid assigning one universal duration to each point value.

| Points in this example team | Reference scope | What makes it this size |
|---|---|---|
| 1 | Update help text in an existing form | Known component, clear wording, small regression surface |
| 2 | Add a filter using an existing API field | Familiar interaction with a few empty-state checks |
| 3 | Add a new filter through the UI and API | More coordinated work with understood behavior |
| 5 | Add a password-reset flow using established services | Several states, security checks, and delivery integration |
| 8 | Introduce a new provider integration | External behavior and failure recovery need investigation |
| 13 | Replace checkout across several markets | Scope is large enough to discuss splitting before commitment |

Another team may size these examples differently. Their architecture, prior experience, and definition of completion are different. Compare stories within the team's own context.

## 3. Compare the work, complexity, and unknowns

Ask three concrete questions:

- What must change, including tests and rollout?
- Which parts are harder than the reference story?
- Which missing facts could materially change the implementation?

Suppose the team already sized a category filter at three points. A price filter may be similar if the API supports a range query. If it requires a new search index and a data migration, the original reference no longer explains the full work. Record that difference instead of adding an arbitrary time multiplier.

## 4. Vote independently, then discuss the spread

Use a scale such as 1, 2, 3, 5, 8, and 13. Ask participants to choose before revealing votes. Let someone with a high estimate and someone with a low estimate explain the assumptions behind their choices.

In this fictional workshop, a mobile layout fix receives votes of 1, 2, and 5. The high voter knows that a supported Safari version uses a different rendering path. After the team reproduces that behavior and agrees on a test plan, it votes again. The useful result is the shared understanding; mechanically averaging the votes would hide it.

For facilitation and remote participation, see [How to Run Remote Planning Poker](/guides/how-to-run-remote-planning-poker).

## 5. Split or investigate work the team cannot size

A large number can signal excessive scope, but the right boundary depends on the team. If the story contains several independent outcomes, split it. If a single unknown dominates the estimate, agree on a timeboxed investigation with a specific question and a useful output.

For a payment integration, an investigation might answer whether the provider supports the required retry behavior. The output could be a small proof of concept, documented failure states, and refined acceptance criteria. Do not use a large estimate to conceal an unanswered architectural question.

Use the [epic breakdown guide](/guides/how-to-break-down-epics-into-user-stories) to find slices that retain a user outcome.

## 6. Use completed work to inform sprint planning

Track points completed under the same Definition of Done. For a fictional team that completed 18, 22, 20, and 19 points in four comparable sprints, the arithmetic average is 19.75 points. Treat that history as one input to the next plan, alongside the sprint goal, leave, support duties, and dependencies.

An average does not guarantee the next sprint's result. A changing team or unusually different work reduces the usefulness of the comparison. Use the [Velocity Tracker](/tools/velocity-tracker) to review trends and the [Sprint Capacity Calculator](/tools/sprint-capacity-calculator) to make availability assumptions visible.

## Copy this estimation record

```markdown
## Story estimate
Story: [link and user outcome]
Reference story: [completed work used for comparison]
Agreed estimate: [team's point value]

## Scope included
- [Implementation, testing, review, and release expectations]

## Reasons for the size
- [Difference from the reference story]
- [Complexity or external dependency]

## Unresolved questions
- [Question, owner, and next action]

## Decision
[Ready to plan / split the story / investigate first]
```

## Common mistakes to avoid

Avoid turning points into individual productivity targets or comparing team velocities as a ranking. Do not retroactively increase completed points to make the numbers match effort spent. If the work changes substantially, discuss the scope change and preserve enough history to understand it.

A calculator result is a heuristic, not team consensus. Use it to expose assumptions, then confirm the estimate with the people doing the work. For a concrete sprint-readiness review, use the [Sprint Planning Checklist](/tools/sprint-planning-checklist).

## Frequently asked questions

### How many hours is one story point?

There is no universal conversion. Points express relative size within a team; a fixed hours table obscures differences in complexity and uncertainty.

### Should stories be re-estimated when scope changes?

Discuss material scope changes and their effect on the sprint goal. During refinement, update the estimate as understanding improves. During a sprint, make changed work visible rather than rewriting estimates just to improve reported velocity.

### What if team members cannot agree?

Ask which assumptions explain the difference. Clarify the requirements, examine the risk, split the story, or investigate the unknown. Do not force a precise estimate before the team understands the work.

### Can several people work on one story?

Yes. Size the complete outcome, including coordination and testing. Split by valuable outcomes when useful, rather than automatically creating one story per person.
