A bad Jira ticket wastes hours. A good Jira ticket saves them.

This guide covers what separates a useful ticket from one that gets bounced back, ignored, or misunderstood.

## Start with a complete before-and-after example

“Checkout is broken; please fix” does not tell a developer where to begin. The following fictional example adds the minimum information another person needs to reproduce and verify the issue. Adapt the details to your product rather than copying the sample environment as fact.

```markdown
## Title
Checkout submits twice when Pay is pressed repeatedly on mobile

## Context
A shopper can submit the payment form again while the first request is pending.

## Steps to reproduce
1. Open the staging checkout with an in-stock item.
2. Enter a valid test payment method.
3. Enable a slow network profile and press Pay twice before a result appears.

## Expected
One payment attempt leads to one order. Pending progress is visible.

## Actual
Two submissions appear in the request log; confirm whether both create charges.

## Environment and evidence
[Device, browser, application build, request IDs, and a recording]

## Acceptance criteria
- A pending payment has a visible state.
- Repeated submission does not create another paid order.
- A declined attempt can be retried safely.

## Open question
Does the payment service already support idempotent requests?
```

Notice that the example separates observed duplicate requests from an unconfirmed duplicate charge. Keep observations, assumptions, and questions distinct so the team investigates the actual failure.

## Review the draft before you hand it to a developer

Try this short exercise with the example above. One person acts as the reporter and another as the person who must reproduce the failure. Give the reviewer only the ticket, then ask them to identify the first action they would take.

| Review question | Evidence needed in this example |
|---|---|
| Can someone reproduce the issue? | Starting page, test data, network condition, and the repeated action |
| What was actually observed? | Two requests in the log; duplicate charges are still unconfirmed |
| What would prove the fix? | One paid order from repeated submission, plus a safe declined-payment retry |
| What could change the implementation? | Whether the payment service supports idempotency |

If the reviewer has to invent a detail, add it as an open question or collect the missing evidence. Do not turn a guess into a reported fact.

## 1. Write a Specific Title

The title is the most important field. It should describe the problem or feature in one sentence — specific enough that anyone reading the backlog knows exactly what the ticket is about.

**Bad titles:**
- "Login broken"
- "Fix button"
- "Backend issue"

**Good titles:**
- "Login button does not respond when clicked in Chrome 114"
- "Password reset email not delivered to Gmail addresses"
- "Add rate limiting to POST /api/auth/login endpoint"

**The rule:** If someone reads only the title, they should understand what needs to be done and roughly why.

## 2. Include the Right Description Fields

For **bug reports**, always include:

- **Steps to Reproduce** — Numbered, specific, repeatable
- **Expected Result** — What should happen
- **Actual Result** — What does happen
- **Environment** — Browser, OS, version, URL

For **feature tickets**, always include:

- **User Story** — As a [user], I want to [action], so that [value]
- **Acceptance Criteria** — Specific, testable conditions
- **Design / Mockups** — If applicable

## 3. Write Acceptance Criteria Before Development Starts

Acceptance criteria define what "done" means. Without them, developers guess, QA guesses, and the ticket gets reopened.

**Write them before the sprint starts.** The conversation during sprint planning that leads to clear acceptance criteria often reveals misunderstandings before a single line of code is written.

**Good acceptance criteria are:**
- Testable — QA can write a test case from them
- Specific — Not "the form should work" but "when valid data is submitted, the API returns HTTP 200 and the user receives a confirmation email"
- Inclusive of error states — Happy path only is not enough

## 4. Set the Right Priority

Agree on priority using business impact, urgency, available workarounds, and your team’s incident policy. The labels and response expectations below are examples to adapt to your organization.

| Priority | Meaning |
|---|---|
| Critical | Severe service, data, or security impact. Follow the incident response policy. |
| High | Important workflow blocked without a useful workaround. Agree on urgency with the owner. |
| Medium | Meaningful impact with a usable workaround. Prioritize against other planned work. |
| Low | Cosmetic issue or minor annoyance. Fix when time allows. |

Don't mark everything High. If everything is high priority, nothing is.

## 5. Attach Evidence

A screenshot, recording, or relevant log helps another person investigate. Attach the evidence that explains this issue:

- Browser console errors
- Network tab screenshots
- Stack traces from logs
- A screen recording if the bug is intermittent

## 6. Link Related Tickets

If this ticket blocks another or is related to a recent change, link them. Jira's issue links feature exists for this. Use it.

## 7. Assign to the Right Team

An unassigned ticket in a large backlog is a ticket that will not be looked at. Assign to a team or a specific person. If you don't know who should own it, tag your team lead.

## Common Mistakes

- **Title that describes the symptom, not the problem** — "Page is slow" vs "Dashboard API takes 8+ seconds to load for accounts with >1000 items"
- **Missing steps to reproduce** — Another person has to reconstruct the conditions before investigating
- **No acceptance criteria** — The ticket gets closed and the bug comes back
- **Screenshots not attached** — "I saw an error" without showing the error
- **Marking everything Critical** — Real critical tickets get ignored when everything is critical

## FAQ

**How long should a Jira ticket description be?**
Include enough context to reproduce, implement, and verify the outcome. Split independent outcomes when useful; reading time alone does not determine ticket size.

**Should developers write their own tickets?**
Yes, when they find bugs or need to track technical work. Technical tasks, debt, and infrastructure work should be in Jira so the team has full visibility.

**How specific should steps to reproduce be?**
Specific enough that someone who has never seen the bug can reproduce it by following the steps. Include the URL, the data they should enter, and the exact action to take.
