## Complete Jira Ticket Template

Use this **Jira ticket template** to write clearer bug, story, task, and feature tickets in minutes. Copy, paste, and adapt each section by issue type.

## Choose the right ticket type

| You need to describe | Start with | Make the outcome verifiable with |
|---|---|---|
| Existing behavior that is broken | Bug Report Ticket | Reproduction steps and expected behavior |
| A capability someone needs | User Story Ticket | A user outcome and acceptance criteria |
| A bounded maintenance activity | Technical Task Ticket | A deliverable and a validation plan |
| A proposed product change | Feature / Improvement Ticket | The problem, scope, and success conditions |

Use the Quick copy selector above to choose a section. Paste it into your issue description, replace the placeholders, and move issue type and priority into your Jira project's own fields. Custom fields and supported formatting vary by project.

## Bug Report Ticket

```
## Title
[Clear, specific bug description — not the symptom, the problem]

## Issue Type
Bug

## Priority
Critical / High / Medium / Low

## Description
[2–3 sentences explaining what the bug is and why it matters]

## Steps to Reproduce
1. [Specific, numbered steps]
2. [Anyone should be able to follow these]
3. [Include prerequisites if needed]

## Expected Result
[What should have happened]

## Actual Result
[What actually happened]

## Environment
- Browser: Chrome 124 (or N/A if not applicable)
- OS: macOS 14.2
- App Version: v2.1.5
- URL: https://app.example.com/specific-page

## Acceptance Criteria
- [ ] Bug is no longer reproducible following the steps above
- [ ] Expected result is met in all affected browsers/OS
- [ ] Regression checks pass for related functionality
- [ ] QA can verify with a clear pass/fail outcome

## Attachments
[Screenshots, error logs, video of the issue reproducing]
```

## User Story Ticket

```
## Title
[Feature name or goal, e.g., "Filter products by category on the shop page"]

## Issue Type
Story / Task / Improvement

## Priority
High / Medium / Low

## User Story
As a [user type — e.g., logged-in shopper],
I want to [specific goal],
So that [business value or benefit].

## Description
[Additional context: why this matters, any constraints, dependencies]

## Acceptance Criteria
- [ ] Given [precondition], when [user action], then [expected outcome]
- [ ] [Specific testable condition relevant to this story]
- [ ] [Performance/accessibility/security requirement if applicable]
- [ ] [Edge case handling if relevant]

## Story Points
[ ] 1  [ ] 2  [ ] 3  [ ] 5  [ ] 8  [ ] 13

## Dependencies
- Blocked by: [link to other ticket if applicable]
- Related to: [other relevant tickets]
- Requires API: [API name and version]

## Definition of Done
- [ ] Code is reviewed and approved
- [ ] Tests pass (unit, integration, E2E)
- [ ] No console errors or warnings
- [ ] Accessibility baseline met (keyboard + screen reader labels)
- [ ] Product Owner has accepted the story

## Out of Scope
[Explicitly list what's NOT included in this story]
```

## Feature / Improvement Ticket

```
## Title
[Feature name — keep it clear and concise]

## Issue Type
Task / Improvement / Feature

## Priority
High / Medium / Low

## Summary
[Why are we building this? What problem does it solve?]

## Requirements
- Requirement 1: [Specific, testable condition]
- Requirement 2: [Must include acceptance criteria]
- Requirement 3: [Link to design, spec, or user feedback if available]

## Acceptance Criteria
- [ ] [Functional requirement 1]
- [ ] [Functional requirement 2]
- [ ] [Performance requirement if applicable]
- [ ] [Security/compliance check if applicable]
- [ ] [Mobile/responsive check if applicable]

## Technical Notes
[Implementation hints, gotchas, architecture considerations]

## Testing
- Unit tests: [coverage target or specific test scenarios]
- Integration tests: [what to test across services]
- Manual QA focus: [edge cases, user flows to prioritize]

## Definition of Done
- [ ] Code peer-reviewed
- [ ] Tests written and passing
- [ ] Documentation updated (README, API docs, etc.)
- [ ] No new technical debt introduced
- [ ] Product Owner sign-off
```

## Technical Task Ticket

```markdown
## Title
[Describe the concrete change and the affected system]

## Issue Type
Task

## Objective
[Why this work is needed and who benefits]

## Scope
- [The component, service, configuration, or data to change]

## Acceptance Criteria
- [ ] [Observable result that confirms the change]
- [ ] [Regression or compatibility check]
- [ ] [Rollout or rollback check where relevant]

## Validation
[Commands, test cases, dashboards, or review evidence]

## Dependencies
[Required access, linked work, or external decisions]

## Out of Scope
[Related work that belongs in a different ticket]
```

A useful task might be “Rotate the staging webhook signing secret and verify delivery.” Its validation should explain how the team checks the new secret and how a failed rollout is recovered. Avoid a title such as “Webhook cleanup” that leaves the deliverable undefined.

## What Every Jira Ticket Needs

Regardless of type, **always include:**

1. **Clear Title** — Specific, describes the problem or goal (not "Fix bug" — "Login button unresponsive on Safari 17")
2. **Issue Type** — Bug / Story / Task / Improvement / Epic
3. **Priority** — Critical / High / Medium / Low (be honest)
4. **Description** — Context, why it matters, any relevant history
5. **Steps/Requirements** — Specific, testable, repeatable
6. **Acceptance Criteria** — How do we know it's done? (use checklists or BDD format)
7. **Dependencies** — Blocked by? Relates to? Requires?

## Pro Tips

- **Use consistent formatting:** Markdown headers, bullet lists, numbered steps make tickets scannable
- **Link related tickets:** Use `[]` links or Jira's native linking to keep context connected
- **Attach evidence:** Screenshots for UI bugs, error logs for backend issues, design mocks for features
- **Set realistic priority:** If everything is "Critical," nothing is
- **Include acceptance criteria checklist:** Teams should know exactly when this ticket is done
- **Keep it under 500 words:** If your ticket is longer, break it into sub-tasks
